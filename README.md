# REAL LIFE TYCOON: Café Empire

> Permainan simulasi perniagaan mudah alih: urus kafe kecil di Malaysia, tetapkan harga, beli stok, ambil staf, hadapi peristiwa harian dan kembangkan empayar kafe anda. Bahasa Melayu, mata wang RM.

A single-player, mobile-first browser game built with React, TypeScript (strict), Vite, Tailwind CSS and Recharts. The game runs entirely in the browser. There is no backend, no account and no payment, and progress is saved only in the current browser's `localStorage`.

All prices, costs, demand figures and events are **fictional game-balancing values**, not real market data.

---

## Quick start

Requires Node.js 20.19 or newer.

```bash
npm install          # install pinned dependencies
npm run dev          # start the dev server (http://localhost:5173)
npm test             # run the Vitest suite once
npm run test:e2e     # Playwright end-to-end tests (builds and serves the app on port 4174)
npm run typecheck    # strict TypeScript check (app and e2e code)
npm run build        # typecheck + production build into dist/
npm run preview      # serve the production build (http://localhost:4173)
```

The build uses a relative base (`./`), so you can host `dist/` from any static host or sub-path. `dist/sw.js` is generated by a small plugin in `vite.config.ts`; service workers need HTTPS (or localhost).

## How to play

1. **Prepare (Persediaan).** Buy stock under *Menu → Inventori*, set prices under *Menu → Menu & harga*, hire staff or buy upgrades under *Urus*, and choose a promotion under *Operasi*.
2. **Open the café (Buka kafe).** The day is simulated hour by hour from 08:00 to 20:00. Footfall depends on reputation, weekday, promotion, upgrades and events. Each customer picks an item, decides whether the price is acceptable, and may be turned away by stock-outs, queues (service capacity) or closures.
3. **Close.** Wages, rent and utilities are paid. Unsold croissants (≈40%) and latte milk (≈5%) spoil overnight.
4. **Review the report.** It includes P&L, cash flow, customer breakdown, product performance, event outcome, timeline, transactions, reconciliation checks and a shareable result card. Then start the next day.

Short of cash? *Kewangan → Pinjaman* offers bank loans (fictional terms). The money arrives at once; from the next day one installment of principal plus flat interest is charged at every close, even if cash runs short. A loan can be cancelled free on the day it is taken, or paid off early later for the remaining principal plus one day's interest.

Objectives award XP. XP raises the café level (Kafe Kecil → Kafe Kejiranan → Kafe Popular → Empayar Kafe), which unlocks higher-tier upgrades and the influencer promotion. If cash stays negative after **3 consecutive closes**, the café goes bankrupt.

## Features

- **Pricing and menu:** per-product price editor with a live margin and price-perception preview, plus menu on/off toggles.
- **Inventory:** purchases with quick quantities, bulk discounts (50+ units 5%, 100+ units 8%), a one-tap restock to the forecast, low/out-of-stock warnings and insufficient-funds states.
- **Demand model:** reputation, weekday, price elasticity, promotions, upgrades, events, substitution on stock-outs and price objections, and drink→croissant add-ons.
- **Service capacity:** hourly order capacity from staff (baristas and cashiers) and upgrades. Customers beyond capacity leave.
- **Staff:** three deterministic candidates each day, a hiring fee, daily wages, firing with confirmation, and staff slots (2, or 4 with an upgrade). The team's names are recorded at the start of each day, so hiring or firing never renames or duplicates the day's candidates.
- **Upgrades (9):** capital investments that affect capacity, footfall, demand, spoilage, reputation, utilities, staff slots or supplier cost, gated by café level.
- **Promotions (5):** none, social media, flyers, a 10% discount, and an influencer (level 2).
- **Events (15):** forecast events are visible during preparation and apply from opening (weather, festivals, a supplier price spike and more). Surprise events are revealed on opening and take effect from the hour they happen; for example, the espresso machine breaks at 11:00 and the viral post lands at 12:00 (others include a food reviewer, health inspection, bulk office order and power outage). Some are mitigated by upgrades.
- **Bank loans (3):** RM2,000 / RM5,000 / RM12,000 over 10 / 20 / 30 days at 5% / 8% / 12% flat interest, gated by café level, one at a time. Installments are exact to the sen (the last one absorbs rounding). Early settlement, a dashboard debt hint and the day's installment in the fixed-cost forecast.
- **Objectives (15) and levels (4).** Savings objectives count cash net of loan principal, so borrowed money never completes them.
- **Reports:** a reconciled P&L, cash flow, an inventory bridge, a debt bridge, 12 automatic reconciliation checks, a shareable PNG result card (Web Share API with a download fallback) and copyable text.
- **Weekly summaries:** every 7th day's report (Sunday) opens with a summary of the week (revenue, net profit, customers, profitable days, best day, service rate, cash and reputation movement) compared with the previous week. *Kewangan → Laporan → Mingguan* lists every week, marking the week still being played and any week cut short by the history limit; comparisons are only made between two complete weeks.
- **Finance:** revenue vs net-profit chart, cash chart, table view, expense breakdown, daily and weekly report history, a transaction ledger and loans.
- **Persistence:** a versioned save with autosave after every action, validation, migration, corrupt-save backup and recovery (a backup this build can load can be restored from Settings), and confirmed reset (also when restarting after bankruptcy).
- **Offline & install:** a web app manifest and a build-generated service worker precache every built file (including the lazy charts chunk), so after the first visit the game installs to the home screen and plays fully offline. Pages are fetched network-first so updates arrive whenever online. The worker only handles the game's own shell and files, keeps its caches separate per deployment (so several copies can share an origin), precaches with `cache: 'reload'` so the shell always matches its chunks, and gets a new version whenever any precached file changes.
- **Backup & device transfer:** Settings can export the save as a JSON file and import one back (validated and migrated exactly like a stored save, with a confirmation before replacing the current game).
- **Multi-tab safety:** every save write carries a random `saveId`. A tab adopts progress saved by another tab when the `storage` event arrives and re-checks whenever it becomes visible again. Before any game-changing action or manual save it also checks the stored `saveId`, so a stale or suspended tab adopts the newer save and shows a toast instead of overwriting it or settling a day twice. Across game versions: an older build cannot read newer saves, so when a tab still running one saves, the current tab decides which game stays in the main save — within one game the further-ahead copy; between different games its own, unless it is bankrupt or unplayed and the other is not — and sets the other aside as a kept copy (restorable from Settings) unless it is just an earlier point of the one that stays; a build that finds a save from a newer version becomes read-only and asks for a reload instead of touching it.
- **UX:** portrait-first, works from 360px wide, ≥40px touch targets, five-tab bottom navigation, confirmation dialogs for destructive or expensive actions, toasts for every action outcome, and loading, empty, error and insufficient-funds states. Honours `prefers-reduced-motion`.

### Key design rules

- **Money is integer sen everywhere** (`…Sen` fields). Rates are applied with integer basis-point maths and rounded immediately (`applyBps`, `mulDivRound`). Ringgit floats appear only in chart axis labels.
- **The UI never calculates financial results.** Components render values from `engine.ts`, `selectors.ts`, `economy.quotePurchase` and `reports.ts`.
- **Each day is processed exactly once.** `openCafe(state, day)` is rejected unless `day === state.day`, the phase is `prep`, and `lastSettledDay < day`. The reducer is pure, so React StrictMode double-invocation is harmless. Repeated taps are ignored silently, and the button also disables itself.
- **Determinism.** Events, demand and candidates come from `hash(seed, day, purpose)`. Reloading cannot re-roll a day, and tests use fixed seeds.
- **Accounting.** Stock purchases reduce cash immediately and increase inventory value. COGS is recognised only when units sell, using weighted-average cost. When the last unit leaves, the remaining value is released, so no rounding residue is left. Spoilage is a non-cash write-off shown under *Lain-lain*. Upgrades are capital spending: they reduce cash but are not expensed. Loans are financing: the money received and principal repaid move cash and debt but not profit; only interest is an expense (under *Lain-lain*).

### Report reconciliation

`reconcileReport()` verifies every report (shown in the UI under *Semakan laporan*):

- opening cash + Σ transactions = closing cash
- sale transactions = revenue = Σ product-line revenue
- Σ product-line COGS = COGS
- expense lines add up, and cash expenses match their transactions
- net profit = revenue + other income − COGS − expenses
- opening inventory + purchases − COGS − spoilage = closing inventory
- loan transactions = loan received − principal repaid
- opening debt + loan received − principal repaid = closing debt
- net profit − Δinventory − capex + loan received − principal repaid = Δcash

### Save format

- Key: `rlt-cafe-empire/save`. Envelope: `{ schemaVersion: 3, savedAt, saveId, game }`.
- **Migration:** `migrateSave()` upgrades known older formats step by step (v1 → v2 → v3). The v1 prototype format (money in ringgit decimals, no ledger) becomes v2; v2 saves gain the loan fields (no loan, zero debt, zero interest in past reports) to become v3. Both steps are covered by unit and e2e tests. Newer-than-supported versions are rejected.
- **Validation:** `validateGameState()` checks types, integer money, ranges, known IDs, phase consistency and report structure.
- **Write ids:** each write stores a random `saveId` before the game data, so `peekSaveId()` can detect another tab's write without parsing the whole save.
- **Recovery:** if the save is malformed or invalid, the raw text is copied to `rlt-cafe-empire/save-rosak`, a new game starts and the player sees a notice.
- **Kept copies:** `rlt-cafe-empire/salinan` holds up to 3 restorable saves set aside by this build (newest first). Older builds overwrite `save-rosak` whenever they meet a save they cannot read, so the current build copies anything restorable from there into its own list as soon as it sees it (at start-up and on another tab's write). A copy that is only an earlier point of another (compared by content, whichever build wrote it, including changes that record no transaction — name, prices, menu, promotion, firing — checked against that day's report once it is settled; new team members must each match their own hiring; games migrated from v1 are compared by where their day started) is never kept, so snapshots cannot push real progress out. Settings lists every copy that is not just an earlier point of the current game or of another copy, with when it was saved, Restore and Remove, and a start-up notice points to a copy that is further ahead than the loaded game. A game this tab took unchanged from an older build's save is part of that build's line, so it is not copied again when that build saves. Beyond three copies, a copy of the game in play that can no longer be checked against it (its history trimmed away) goes first, then the oldest; copies written by a newer version are left untouched. A late-game save is about 0.3 MB of text; if storage is ever full, the oldest kept copies are dropped before the current game would fail to save.
- **Newer versions:** a save written by a newer version is never treated as corrupt: the game shows a read-only "please reload" screen and neither autosaves nor allows actions, so the newer save is left untouched.
- **Loan consistency:** an active loan must match its own schedule (payments made = days closed since it was taken, amounts paid = equal installments so far, opening debt = remaining principal), so every later close keeps producing a valid save. If `localStorage` is unavailable (for example in private mode), the game still runs in memory and shows a warning.

## Decisions on ambiguous requirements

- **"Configurable unit cost":** unit cost lives in the product state and in `data/products.ts`. Players change it indirectly through the supplier-contract upgrade (−10%), bulk discounts and events (+25% coffee price spike). Prices are set directly.
- **Six screens, five tabs:** Menu and Inventory share the *Menu* tab as sub-tabs. Staff, Upgrades and Objectives sit under *Urus*. Reports, the ledger and loans sit under *Kewangan*. Settings opens from the header.
- **Day flow:** `prep → (open) → closed → next day`. Editing is locked while closed so every transaction belongs to exactly one day's report.
- **Marketing** is charged when the café opens. If cash is no longer sufficient, the promotion is cancelled and noted in the report.
- **Objective rewards** are XP and levels, not cash, to keep the financial statements clean.
- **Hiring** charges a one-off fee (other expenses). Firing is free but requires confirmation, and the last barista cannot be fired.
- **Imagery:** the café scene is a lightweight hand-built SVG illustration (morning and evening variants) instead of photographs. This keeps the app small and offline-friendly, and avoids licensing questions.

## Known limitations

- Saves are local to one browser on one device, and there is no cloud sync. Use Settings → export/import to back up a game or move it to another device. Clearing site data without an exported file erases progress. Playing in two tabs is safe but not simultaneous: the most recent save wins and the other tab follows it.
- Single café only. There is no multi-branch "empire" layer, ingredient-level recipes, staff morale or depreciation.
- Report history keeps the latest 60 days. Lifetime totals are kept in stats.
- Balance is tuned with a scripted bot over ~45 days and would benefit from playtesting.

### Note on dependency pinning

All versions are pinned exactly. `package.json` contains `"overrides": { "vite": "$vite" }` because npm 10's peer resolver otherwise tries to pull Vite 8 (and through it Vitest 5) for Vitest's optional peers and crashes. The override keeps the whole tree on the declared Vite 6.4.5. `npm audit` reports 0 vulnerabilities.
